# 模拟器与三个视图（`dev-beyond-simulator`）

> 需求边界、六轮决策与工单见 [`需求边界清单_融合beyond-simulator_2026-09-24.md`](需求边界清单_融合beyond-simulator_2026-09-24.md)。

## 0. 先说清楚：它在流程里的位置 = **预测试**

> 这一节是「模拟器到底是什么」的一句话答案 —— 2026-09-24 由作者提问补上（「按我理解是预测试模式，是我想的这样吗」）。

```
改代码 → ① 模拟器预测试（游戏外，同一套 Lua + 同一套控件语义）
       → ② 真机试玩（人点按钮；这一步没有自动化通道，也不做）
       → ③ 真机取证（日志 / 截图 / 探针）
```

**能拦下的**（可自动判定）：脚本跑没跑 · 控件建没建 / 建了几个 · 变量与信号对不对 · 布局歪不歪 · 动画动不动。
**拦不下的**（只能真机验）：官方素材 · 真机渲染 · 联机 · 性能 · 手感。所以纪律是那句 —— **模拟器通过 ≠ 真机通过**。

### 三档，共用同一份工程与同一个会话（只理解成"预测试"会漏掉③）

| 档 | 用什么 | 时间怎么走 | 给谁 |
|---|---|---|---|
| **① 静态预览** | `op=state` / `op=controls` / `op=shot` | 不跑 | 看工程长什么样 |
| **② 交互试玩** | `op=play`、面板「模拟器」页、浏览器页 `GET /miliastra/play` | **真在走**（引擎 30FPS 时钟），人可点可拖可按键 | 人玩、AI 观察（`get` / 日志 / `history`） |
| **③ 确定性判定** | `op=verify` / `cases[]` / `fromHistory` / `op=frames` | **冻结时钟**，按时间点精确推进 | AI 自己判（可复现） |

② 与 ③ 是最容易混的：**②是"活的一局"，③是"可复现的重放"**。`verify` 会**开一个全新会话**再按 `t` 重放，
所以同一调用两次结果一样 —— 这也是为什么 `fromHistory` 之后「人那局就结束了」（它把活的一局**转成**了确定性用例）。

### 三条边界（别把它当官方模拟器）

1. **不是官方的，也不是真机**：服务端只覆盖变量与信号（**不含**官方完整节点图）；图片只代理 `100001–100006`，其他显示缺失框；1–8 人是**本地多客户端模拟**，不含真实联机。
2. **不替代人点试玩**：②那档的点/拖/按键是**注入到引擎里**的，不是在替你操作真机（不读内存、不连游戏端口、不冒充编辑器）。
3. **两个方向的 GIA 交换都还是 `pending`**：我们导出的 `.gia` 能否被官方编辑器接受（未验证）；**官方编辑器导出的** `.gia` / Authoring JSON 能否被 `op=import` 吃进来（也未验证）。
   已验证的只有引擎侧往返（自己导出的导回来，控件数一致）。
   ⚠️ 所以「**能不能拿我真机的工程进来预测试**」这件事，目前还差最后这一环节 —— 而它只能人来试（见 §6）。

## 3. 三个 tab 怎么挂上去的

落点是 DSH 官方槽位 **`conversation.view`**（会话区顶部 tab），注册形态与侧边栏入口完全一样：

```js
ctx.slots.inject('conversation.view', () =>
  ctx.slots.register({ name: 'conversation.view', id, order, label: () => '…' }, Component))
```

契约出处（本机 DSH `0.1.5-rc.1` 实测）：`dsh-client-ui-conversation/lib/client.js` 用 `renderSlot("conversation.view", …, { only: active.id })` 渲染正文、用 `slots.entries("conversation.view")` 生成 tab 列表，`label` 由 `resolveSlotLabel` 解析（函数或字符串都行）；`ViewTab = { id, label }`。

| tab | id | 内容 |
|---|---|---|
| 初级功能 | `dsh-miliastra-basic` | ① 关卡 + ② 代码（现有卡片，浮层里那一套原样复用） |
| 高级功能 | `dsh-miliastra-advanced` | ③ 日志与画面（含「高级诊断」折叠区：读界面控件 / 探针） |
| 模拟器 | `dsh-miliastra-simulator` | 工程与控件树 + 画面 PNG + 试玩日志 + 8 个动作按钮（编辑器画面 / 开始试玩 / 单步 / 刷新画面 / 停止 / 居中点击 / 导出 GIA / 重置工程） |

两个要点：
- **同一个 `Panel`** 既当侧边栏浮层（`inline:false`）也当全宽视图（`inline:true` + `group`）。侧边栏入口**保留**，没有砍掉。
- 官方按 `{ only: active.id }` **只挂载当前选中的 view**，所以三个 tab 不会各自 15 秒轮询 —— 只有可见的那个在跑。

> ⚠️ **两处入口，同一套页面**（第一轮实测踩过：三个 tab 渲染在**会话区 header 的 tablist** 里，`tabs.length > 1` 才出现，作者在侧边栏找了半天没找到）：
> 1. **会话区顶部**：`初级功能 / 高级功能 / 模拟器` 三个 tab（`conversation.view`，与官方「对话 / 轨迹」并列）；
> 2. **侧边栏浮层内**：面板顶部一条**平铺成三等分**的页面条 `初级功能 / 高级功能 / 模拟器`（默认初级）。
>
> **三个页面各自独立、互不干扰，内容平铺铺满**：初级 = ①②、高级 = ③、模拟器 = 引擎页；每页用 `-bodyfill` 铺满宽度（不再留一个空洞的第三栏）。
> **没有「全部」混合页**（作者 2026-09-24 明确要求去掉）。模拟器页在两处**共用同一个正文组件 `SimulatorBody`** —— 状态与动作只有一份，不会两套漂移。

## 4. 画面怎么来的（为什么不需要开游戏）

`miliastra_sim op=shot`：
- `target=ui` → `renderEditorPng(工程快照)`：编辑器视图（容器/控件框 + 选中态）
- `target=play` → `renderScenePng(试玩场景树)`：**当前试玩帧**

两者都在 **Host 进程内用原生 canvas（`@napi-rs/canvas`）画成 PNG**，然后落进插件数据目录的 `shots/`（命名 `sim-ui-*` / `sim-play-*`，与真机截图同一套命名与清理纪律），面板直接用既有的 `/miliastra/shot?name=…` 显示。
所以：**不需要开游戏、也不要求窗口在前台** —— 这是它与 `miliastra_shot`（抓真窗口）最大的区别。

**连帧用 `reuse:true`**：写**固定名** `sim-play-live.png` / `sim-ui-live.png`（覆盖），URL 带 `&t=<时间戳>` 绕开 `/shot` 路由的 immutable 缓存。
为什么必须这样做：连帧是 5fps，**一小时就是 18 000 张图** —— 每帧新建文件等于把用户的 `shots/` 刷爆。留证据要一张一张存时不要传 `reuse`。

## 4.5 面板上怎么玩（2026-09-24 补齐）

引擎在 Worker 里**本来就以 30 FPS 固定步长自走**（`host/worker.js` 的 `setInterval(33ms)`、`FIXED_DT=1/30`、最多 5 步追帧）。面板只负责**取帧 + 送输入**：

| 动作 | 做什么 | 注意 |
|---|---|---|
| 开始试玩 | `play start`（带 `canvasId` 与 `playerCount=1–8`） | 换人/换设备要重开或走下面两个动作 |
| **连帧：开** | 每 200ms 取一帧 ≈ **5 FPS**，看动画/状态在走 | **不是 60 FPS 动作游戏**（那条路要浏览器端 WebGL 渲染，还没做） |
| **点画布任意位置** | 在 PNG 上点一下 = 往引擎注入一次点击 | 坐标按**左下原点**换算（`stagePointFromEvent`，纯函数、有回归）；点错地方不会报错，所以必须能测 |
| 按键 | 按钮来自 **`op=keys`**（从你脚本源码扫 `KeyEventType` 名字），另有输入框可填任意键名 | 脚本里没写 `KeyEventType` 就用引擎的官方键名预设 |
| 单步 | 先 `pause` 再 `step`（跑着的时候那个 30FPS 时钟自己也走） | 单帧确定性调试用 |
| 设备 | `play device`，可选五档画布（来自 `state.canvas.presets`） | ⚠️ **`device` 会重建运行时** —— 见下面的陷阱 |
| 人数 / 视角 | `playerCount` 在 `start` 时生效；`view` 随时切当前看谁 | 视角可选范围**跟着人数收敛**（1..人数） |

> ⚠️ **踩过的陷阱（已修 + 已进回归）**：引擎的 `device` 会**重建整个运行时**。切设备时若不把 `playerCount` 一起带上，人数会**悄悄掉回 1**，随后 `view 2` 报 `playerIndex must be an integer 1-1`。
> 现在 **Host 侧记住 `start` 的人数、切设备时自动沿用**（`lib/sim.mjs` 的 `startOpts`），面板也会显式传；报错信息里也写清了成因与解法。

能玩的边界（别夸大）：**点按钮 / 看状态变化 / 单步调试 / 切设备与人数** 都行；**需要连续操作的动作类玩法不行**（5fps + 每次点击一次网络往返）。

### 页面分区（2026-09-24 按作者要求：**1:2**）

```
┌ 模拟器 ────────────────────────────────────────────── [刷新] ┐
│ 1 份（左列，**自己滚**）        │ 2 份（右，**不动**）         │
│ ① 画面与日志（缩略，横排）      │ 试玩页（iframe）             │
│ ② 试玩操作 + 操作时间线         │   src = /miliastra/play      │
│ ③ 验收单（自动项 + 人工项）      │   PixiJS WebGL，人真能玩      │
│ ④ 工程与控件树 / 工程适配（折叠）│   与 AI 共用同一个会话/工程    │
└───────────────────────────────────────────────────────────────┘
```

- **tab 就是 1:2**（`grid-template-columns:minmax(300px,1fr) 2fr`）：右边那 2 份是**试玩页 iframe**（`GET /miliastra/play`）。
  不把 pixi 塞进面板的理由：WebGL 与自己的 CSP 处理，独立页最稳；面板里只留缩略图与操作面。
- **人**：直接在 iframe 里点 / 按键（引擎把这一局记成 history）。
  **AI**：用 `miliastra_sim op=play`（`key`/`pointer`/`step`）驱动**同一个会话** —— 页面每 33ms 轮询场景（`sceneRev` 增量），
  所以 AI 那边一动，这里画面跟着变；反过来，人玩完那一局，AI 用 `op=verify fromHistory:true` 直接变成回归用例。
- **滚动模型**：`-simbody` **不滚**，**左列自己滚**、右列不动 ——
  否则左列一长，滚下去 iframe 就出了视野（作者实测反馈「右侧啥都没」就是这么来的）。
- **左列顺序 = "最常看的在最上面"**：① 画面与日志（+ 4 个核心动作）→ ② 试玩操作（**高级项折叠**）→ ③ 操作时间线 → ④ 验收单 → ⑤ 工程与控件树 / 工程适配（**折叠**）。
  作者实测反馈「画面在左下角」= 画面被「工程与控件树 + 工程适配」那两块挤到下面去了。
  ⚠️ 另一个坑：左列是**固定高度的 flex 列**，子项默认 `flex-shrink:1` + `min-height:0` ——
  内容一超就被**压扁并互相重叠**（作者截图里"按钮/文字叠在一起"就是这个，不是渲染 bug）。
  现在子项一律 `flex:0 0 auto` + `min-height:auto`，滚动交给容器自己。
- **左列宽度下限 300px**（`minmax(300px,1fr)`）：880px 浮层的 1/3 只有 285px，塞不下这些按钮。
- ⚠️ **重启 `dsh web` 之后工程会回到「出厂默认」**（Host 是启动快照）：`op=state` 的 `factoryDefault:true` 会如实说，
  面板顶部会出现一条粉色提示 + **「一键重搭上次：《双相》」**（用成功 bind 时记下的配方 `last-bind.json`）。
  **不自动重搭** —— 那会在人没要求的时候改工程。
- ⚠️ **窄屏兜底**：浮层只有 880px 宽，`@media (max-width:1000px)` 时 1:2 塌成**一列**（否则 1/3 宽会挤成一条，什么都看不清）。
  试玩页自己也有 `@media (max-width:820px)`（嵌在 2/3 列里 ≈ 570px 时收一档、标题换成短的，否则工具栏折成两三行把舞台挤没）。
- iframe 能嵌的前提：**`/miliastra/play` 不要求鉴权**（实测 `curl` 直取 `200`；`/` 才是 401），也没有 `X-Frame-Options` / `frame-ancestors` 拦。
- 布局、iframe 的 `src`、左列顺序、滚动模型、折叠卡都进了回归（`client-render-test.mjs`）。

## 4.6 AI 怎么自测逻辑（`op=verify`）★

**一次调用 = 操作 + 断言 + 判定**：

```json
{"op":"verify",
 "steps":[{"key":"KeyboardCraftspersonKey3Down"}],
 "expect":[{"kind":"log","contains":"GOT_KEY_3"}]}
```

→ `{passed:true, failedAt:null, results:[{kind:"log",ok:true,...}], case:{events,asserts}, snapshot:{logs,...}}`

**为什么这么设计**（而不是让 AI 用引擎原生的三跳）：引擎原生是「先交互跑一遍 → `history` → `saveCase` → `runCase`」——对 AI 是三次来回、还要自己算时序。`op=verify` 由 Host 组好用例直接走 `runCase`：它会**开一个全新会话**按 `t` 重放事件、按 `at` 判定断言 ⇒ **每次结果一致**（可重复回归）。
⚠️ `runCase` 需要**活着的 worker**，所以 Host 会先 `start` 一次把**当前**工程送进去（刚 `patch` 的脚本才生效）；重放**不支持 `device` 事件**。

**steps 写法**（事件种类来自引擎 `autotest/runner.js` 的 `applyEvent`）：

| 步骤 | 含义 |
|---|---|
| `{at, after?, key:"KeyboardCraftspersonKey3Down"}` | 注入按键（键名用 `op=keys` 拿） |
| `{click:{x,y}}` | 注入点击（**左下原点**；面板点画布走的也是这条） |
| `{clickName:"预设按钮"}` | 按控件名直接触发点击 |
| **`{drag:{from:[x,y],to:[x,y],steps?,gap?}}`** | **拖拽/滑动**：自动展开成 `down → move… → up`（默认 6 段、每段 0.05 秒）—— 引擎的 `CursorBeginDrag`/`CursorDrag`/`CursorEndDrag` 都在 move 里发，不展开就测不到 |
| `{pointer:{type,x,y}}` | 裸指针事件（`down`/`move`/`up`/`click`），要手排细节时用 |
| `{setVar:{entityType:"PlayerSelf",name:"Gold",value:10}}` | 写服务端自定义变量 |
| `{sendSignal:{name:"EarnGold",params:[1],target:"PlayerSelf"}}` | 发服务端信号 |
| `{view:2}` / `{pause}` / `{resume}` | 切视角 / 暂停 / 继续 |

`at` 省略 = 上一步 + `after`（默认 0.1 秒）；`drag` 占用的时间按 `(steps+1)×gap` 自动顶上。

**expect 断言七种**（引擎 `autotest/assert.js`）：

| kind | 参数 | 判什么 |
|---|---|---|
| `log` | `contains`、可选 `level`、`source:"server"` | 客户端（或服务端）日志里出现过这段字 |
| `control` | `id?`/`name?` + `field` + `equals` | 控件字段等于某值（`text` / `visible` / `pressed` / `interactable`…） |
| `var` | `entityType` + `name` + `equals` | 服务端自定义变量等于某值 |
| `signal` | `name`、可选 `direction:"outbound"`、`values` | 出现过该信号（可带参数） |
| `tree` | `name` + `exists` | 控件存在/不存在（**动态创建验证用这个**；只能按 `name` 找） |
| **`count`** | `name?`/`controlKind?` + `equals` 或 `atLeast` | **建了几个** —— `tree` 只能答「建了吗」，列表项/连击星这类要数数量的只能用它 |
| `lua` | `source` | 跑一小段 Lua 查询脚本，用 `query.var / query.control / query.logContains / query.logs / query.serverLogContains / query.serverLogs / query.signals` 自己判 |

`at` 省略 = **最后一个事件之后 0.1 秒** ⇒ 查的是"这一串操作做完之后的最终状态"，**AI 不需要自己算时序**。

**失败长什么样**（AI 靠它自查，不用回头问人）：

```json
{"passed":false,"failedAt":0.1,"frame":3,
 "results":[{"kind":"var","ok":false,"actual":7,"expected":999,"at":0.1}],
 "hint":"第 1 条断言没过：kind=var 期望 999 实际 7（t=0.1s / frame=3）。看 results 与 snapshot.logs / serverLogs 定位，改完再跑一次 verify。"}
```

默认判定后**停掉会话**（不空烧 Worker 的 30FPS 时钟）；要接着交互就传 `keepRunning:true`。
⚠️ **失败取证会把会话置于暂停**（见 §4.8）——`keepRunning:true` 想接着玩，先 `op=play action=resume`。

> 写脚本要注意的口径（实测踩过）：服务端控件模板里 **`script.Parent` 是 nil**，按键监听正确写法是
> `script.object:AddKeyEventListener(Enum.KeyEventType.X, fn)`（引擎自己的 `runtime.test.mjs:548` 就这么写）。

## 4.7 写断言前先看控件（`op=controls`）

`op=state` 的每条 tree 行有 **12 个字段**（`ancestorIds` / `siblingIndex` / `siblingCount` / `templateId` / `guid` / `childCount` / `incomplete`…）——
对「写一条断言」这件事**全是噪音**。`op=controls` 只回**四个**：`{id, name, kind, depth}`，外加 `names`（可直接抄进 expect）、`kinds`（类型直方图）、`scripts`（已挂脚本）。

```json
{"op":"controls","namedOnly":true}
{"op":"controls","runtime":true}      // 看**运行中**会话的控件树（脚本运行时建出来的那批），需先 start
```

过滤参数：`namedOnly` / `nameContains`（**Host 侧过滤，中文可用**）/ `kind` / `maxDepth` / `limit`（截断回执带 `total`/`omitted`，不静默少给）。

**一条不显然但要紧的规则**（写在这里免得反复试错）：

| 断言 | 按什么找控件 |
|---|---|
| `expect[{kind:"tree"}]` | **只能按 `name`** —— 引擎 `findControl` 对 tree 只认 name ⇒ **没名字的控件断不了 tree** |
| `expect[{kind:"control"}]` | `id` / `name` 都认 |

`runtime:true` 与 `op=state` 的区别：前者是**跑起来之后**的树（脚本 `InstantiateClientUIControl` 建出来的会出现在这里），后者是编辑器工程树。
「哪些控件**能**被脚本动态创建」是另一个问题，问 `miliastra_map op=clientui`（只看无父节点的独立模板）。

⚠️ **两种树形状不一样（实测踩到，已拍平）**：

| | 形状 | 顶层条数 | 字段 |
|---|---|---|---|
| 编辑器树（`state` / `controls`） | **拍平** | 全部（带 `depth`） | 12 个（含 `ancestorIds`/`siblingIndex`…） |
| 运行时树（`controls runtime:true` / verify 取证） | **嵌套**（子控件在 `children`） | **只有 1 条**（「容器节点」） | 40+ 个（含 `box`/颜色/`text`/`instantiated`，**没有 `depth`**） |

`op=controls` 与失败取证都会**先拍平再数**——不拍平会把控件少算一个数量级（实测 **1 vs 17**）。
真实运行时的样子（demo 实测）：`容器节点 → [文本框, 光标检测区域, …, Lua实例化面板 → [模板标题, 模板图标, 确认按钮 → [按钮文字]]]`。

## 4.8 一组用例一次跑 + 失败自动取证（2026-09-24 补）

**① `cases[]`：把「一条规则一次调用」升级成「一次调用跑整组回归」**

```json
{"op":"verify","cases":[
  {"name":"按3加分","steps":[{"key":"KeyboardCraftspersonKey3Down"}],"expect":[{"kind":"log","contains":"SCORE_1"}]},
  {"name":"金币同步","steps":[{"setVar":{"entityType":"PlayerSelf","name":"Gold","value":7}}],"expect":[{"kind":"var","entityType":"PlayerSelf","name":"Gold","equals":7}]}
]}
```

→ `{passed, caseCount, passedCount, failedCount, cases:[{name,passed,failedAt,frame,results,logs?,runtime?,shot?}], failures:[{name,failedAt,hint}], hint}`

- 每个用例**各开一个全新会话**确定性重放 ⇒ **用例之间互不影响**（`tests/sim-test.mjs` 有一条断言专门钉这个：前一个用例按过的键**不会**漏进下一个用例）。
- 默认**跑完全部**（回归语义）；`stopOnFail:true` 则第一个不过就停，回执带 `stoppedEarly:true`。
- 通过的用例**不回 logs、不落图**（不给 AI 加噪音）；没过的回最后 10 行日志。
- `cases[i]` 缺 `expect` 时报错**点名第几个用例**，不是笼统一句。

**② 失败自动取证：`shot` + `runtime.controlNames`**（`shotOnFail:false` 可关掉存图）

`runCase` 的实现是「`playStart` → 在**活着的会话**上重放」，判定返回时会话**还停在失败那一帧**，所以能就地取证：

| 回执字段 | 是什么 | 怎么用 |
|---|---|---|
| `shot` | 失败点附近一帧 PNG（`sim-play-<用例名>-fail-<时间戳>.png`） | `read_image` 看一眼画面；**截图前先把 Worker 时钟 `pause`**，否则 30FPS 会继续往前走（`tickClock` 看 `status.paused`） |
| `runtime.controlNames` | 失败点附近的**运行时**控件名清单 | `tree{name,exists}` / `control{name,…}` 写错时，照着这份清单改期望值 |
| `runtime.controlCount` / `frame` / `time` | 计数与帧号 | 和 `failedAt` / `frame` 对一眼，确认取到的是不是同一处 |

⚠️ **诚实口径**：Worker 每帧 33ms，截图可能比 `failedAt` **晚 0~2 帧**——它是「失败点附近」的画面，不是逐帧精确的定点快照。

## 4.9 浏览器试玩页（W2）——**给人玩的**，但也是 AI 的一条路

`GET /miliastra/play`（面板「模拟器」页有「浏览器试玩 ↗」入口）。一页三件：**PixiJS WebGL 渲染的画面**、工具栏（开始/暂停/单步/重开/结束 + 设备·人数·视角）、侧栏（运行状态 / 服务端变量 / 日志 / **这一局的操作时间线**）。

**为什么需要它**（面板不是已经有 PNG 帧了吗）：面板是 **Host 出 PNG**，够 AI 看"画面对不对"，但人**玩**起来是 5fps 的幻灯片。
浏览器页让画面按 WebGL 真流畅地跑，手感、时序、连招这类只能人自己试的东西才有意义。

**技术形状**（三块，都是复用而不是新造）：

| 块 | 是什么 |
|---|---|
| 画面 | 引擎自己的 `engine/studio/play/pixi-renderer.js`（`PixiPlayRenderer`）+ `browser-session.js`（`createPlaySession`）—— **与上游 DSH 插件/Web 同一条浏览器循环**，搬引擎时就一起进来了 |
| 数据 | `POST /miliastra/engine`（与面板、与 `miliastra_sim` 工具**同一个入口**）⇒ 浏览器里玩的和 AI 操作的是**同一个会话、同一份工程** |
| 产物 | `node tools/build-sim-play.mjs` 用 esbuild 打成**单个 ESM**（552 KB，含 pixi）入库在 `lib/sim-play/dist/play-renderer.js` —— 装插件的人不做构建也能用 |

⚠️ **两个坑**（都已被测试钉住，别踩回去）：

1. **画面必须 `summaryOnly:false`** —— `scene` 是节点级增量场景，默认的"瘦身"会把它砍成 `sceneOmitted`（只留计数）⇒ 页面**黑屏**。
   修的是 `slimPlay`：原来**无条件**丢 `scene`/`paint`，与「summaryOnly 只去体积、`false` 时给全量」的约定矛盾。
2. **产物会过期** —— 改了 browser 侧源码却忘了重打包，页面在浏览器里跑的是**旧引擎**，而且**完全不报错**。
   `tests/sim-play-test.mjs` 现打一份比字节（`--check` 同款判据），`prepublishOnly` 也跑一遍。

### ★ 对 AI 的收益：人玩一局 → 那一局变成回归用例

这是这个页面**对 AI**（而不只是对人）的价值所在：

```
人在 /miliastra/play 里玩 → 报「刚才这么点就错了」
AI：miliastra_sim {"op":"verify","fromHistory":true,"expect":[{"kind":"var","entityType":"PlayerSelf","name":"Gold","equals":3}]}
→ 用**人那一局的真实操作序列**确定性重放 + 判定（AI 不用手抄 events）
```

所以页面**关掉时故意不停局**（`pagehide` 只 `destroy()` 渲染器）—— 一关就 stop 的话 history 归零，这条路就断了。
要停就点页面的「结束」，或让插件卸载（`disposeSimAll` 收干净）。代价是那一局会继续在 Worker 里以 30FPS 走，直到有人停它。

> ⚠️ **「确定回放」的边界**：`runCase` 会**重开会话**再重放 —— 所以 `fromHistory` 之后那一局就结束了；
> 而且它**不认 `device` 事件**（切设备那一步不会被重放）。

## 4.10 动画怎么证明（`op=frames`）★

`verify` 只能断言**某个静态值**（"t=1s 时 `matrix.tx=900`"）。但「动画到底动没动」「动的是不是那一块」这种问题，
两个值答不了 —— 而 AI 看不到动图。`op=frames` 把「两帧一样吗」变成**数字**：

```json
{"op":"frames","frames":[0,0.5,1],"steps":[{"click":{"x":800,"y":450}}]}
```

一次调用 = 按时间点出帧 + **帧间像素差** + **字段级变化**。实测（容器节点做 1 秒线性 Tween 右移 100）：

| 帧 | 文件 | 帧号 |
|---|---|---|
| t=0 | `sim-play-moving-t0-<时间戳>.png` | 0 |
| t=0.5 | `sim-play-moving-t0.5-<时间戳>.png` | 16 |
| t=1 | `sim-play-moving-t1-<时间戳>.png` | 32 |

```json
"diffs":[
 {"from":0,"to":0.5,"identical":false,"changedPixels":9704,"changedRatio":0.006739,"maxDelta":243,
  "bbox":{"x":452,"y":180,"width":737,"height":296},
  "changedControls":[{"id":"1","name":"容器节点","fields":{"matrix.tx":[800,850]}}]},
 {"from":0.5,"to":1,"changedPixels":9704,"bbox":{"x":502,...},"changedControls":[{...,"matrix.tx":[850,900]}]}]
```

**两个独立通道互相印证**（这是它比"只看图"强的地方）：

| 通道 | 读数 | 说明了什么 |
|---|---|---|
| 场景字段（`changedControls`） | `matrix.tx: 800 → 850 → 900` | **哪个控件的哪个字段**变了，能直接定位 |
| 像素（`changedPixels` / `bbox`） | 9704 px、bbox.x `452 → 502`（+50） | 画面**真的**跟着动了，且位移量与字段对得上 |

**负对照也验过**：换成静态工程后 `identical:true` / `changedPixels:0` / `maxDelta:0` / `changedControls:[]`
—— 所以那 9704 不是噪声。**可复现**：同一调用跑两遍，数字一样。

### 两条实现决定（改的时候别绕）

1. **内部用「暂停 + 单步」推进时间**：worker 自己有个 30FPS 的 `setInterval` 在走，不先 `pause` 的话时间会自己往前跑
   —— 帧就对不上时间点，也不可复现（面板的「单步」是同一个机制）。所以 `steps` 里的 `pause`/`resume` 对帧时间没有意义（Host 会把时钟重新冻住）。
2. **每帧回全量场景、由 Host 自己比字段**，不依赖引擎的增量协议。
   ⚠️ 位置**不在** `anchoredPositionX` 上 —— 运行时场景节点是 `{id,parent,z,group,matrix:{a,b,c,d,tx,ty},kind,name,…}`，
   所以「控件移动了」表现为 **`matrix.tx/ty` 变了**（不摊开 `matrix` 这一层，`changedControls` 会永远是空的 —— 实测踩到，已修）。

### 成本与边界（都是显式的，不静默）

- 帧数上限 **12**（每帧一张 PNG + 一次解码）；要推进的步数上限 **1200 步**（`dt` 默认 1/30 秒）——
  超了**直接报错并给出「换更大的 dt」这条路**，不会默默跑十分钟。
- `diff:false` 只出帧不比像素（省一次解码）；`threshold` 默认 8（每通道差值）。
- `bbox` 是**图像像素坐标（左上原点）**；舞台坐标是左下原点，两者 y 相反。
- 帧是**真落盘**的（不自动删，同 §5 纪律）；`keepRunning:true` 可以判定完接着玩，默认跑完就停。
- ⚠️ 帧文件名标签有 **24 字符上限**（`sanitizeLabel`）—— 写长了会把 `t0.5` 截掉（踩过；顺带修了「先剥尾点后截断又留下尾点」的 bug）。

## 4.11 交接值从哪来（`op=handover`）★ 2026-09-24 补

**它解决什么问题**：`bind` 最难的不是搭工程，而是**交接值**。抄错一位 → 脚本的 `InstantiateClientUIControl()`
**静默什么都不建**（不报错、日志里也没痕迹）。而创作者给的号通常就写在脚本常量里，所以"读源码抽真值"比"让人抄一遍"可靠得多。

```
① op=handover                       → 这台机器上有哪些活文件（★ 标出"当前正在开发的那张图"）
② op=handover source=<活文件路径>    → 读那份 Lua：候选交接值 + suggestedTemplates + containerId
```

**双相实测输出（2026-09-24）**：

```json
[{"name":"CONTAINER_INDEX_HANDOVER","value":1073741866,"role":"container","isTemplate":false},
 {"name":"TEXTBOX_TEMPLATE","value":1073741867,"kindHint":"textbox","isTemplate":true},
 {"name":"IMAGE_TEMPLATE","value":1073741868,"kindHint":"image","isTemplate":true}]
"suggestedTemplates": [{...textbox 1073741867...}, {...image 1073741868...}], "containerId": 1073741866
```

- 判据：源码里 `local NAME = <9 位以上整数>` 且值 ≥ `1073741824`（真机 id 的量级）——所以 `local LIMIT = 60` 不会被误收。
- `kindHint` **只看变量名**（IMAGE→image / TEXT→textbox / CONTAINER→role=container）：**控件类型猜错同样静默失败**，
  必须创作者确认。回执里明写这一点。
- 活文件清单**可能为空**（换了机器/账号）——如实回空，不报假警；给了 `source` 就只做抽取。

## 4.12 把真机那份工程搬进来（`op=bind`）★ 2026-09-24 补

**它解决什么问题**：模拟器能跑 Lua，但「让双相在模拟器里跑起来」原来是**手写探针**（建模板 → 存盘 → 手改 JSON 里的 guid → 读回 → 挂脚本 → 起会话）。
这套流程里最容易错的不是技术，是**交接值**：模板索引错一位，脚本的 `InstantiateClientUIControl()` 就**静默什么都不建** —— 看起来"跑起来了"，其实全是空的。所以 `bind` 把这条路变成一个 op，并把交接值摆在明面上。

```
{"op":"bind",
 "source":"…\\Beyond_Local_Save_Level\\1073741833\\external_lua_file\\双相.lua",
 "templates":[{"guid":1073741868,"kind":"image","name":"图片模板"},
              {"guid":1073741867,"kind":"textbox","name":"文本框模板"}],
 "containerId":1073741866}
```

它做的四件事：

| 步 | 做什么 | 为什么这么做 |
|---|---|---|
| ① | `newAsset(client)` + 每个交接值 `addTemplate{guid,kind,name}` | **模板索引（= 顶层节点 guid）就是脚本里用的那个号**；引擎自己另编一个 ⇒ 永远解析不到。`addTemplate` 因此支持显式 `guid`（带合法性与重号校验） |
| ② | `newAsset(server)` + 挂脚本（挂载名 = 文件名，`scriptName` 可改） | 不少脚本用 `script.path` 自查挂载名（双相的 `checkMount()` 就要求 `双相.lua`）——名字不对它会**自己退出** |
| ③ | 交叉核对交接值 | 源码里 10 位以上的整数 ≈ 真机 id：`handover.missing` = 你交的模板索引在源码里找不到；`extra` = 源码里有、你没交的（可能还缺模板）。**启发式，不是判决** |
| ④ | 起一次会话、**先走 `settleSec` 秒再读** | 脚本的构建发生在**进入 RUNNING 之后**：停在 frame 0 读，双相只报 `controlCount=1`（容器自己）—— 会被误读成"什么都没建"（实测踩到） |

**默认值**：`fresh:true`（先把两个资产重置成出厂工程、清掉已有脚本，再重建 ⇒ 同一份参数 → 同一份工程）、
`keepFactory:false`（清掉出厂橱窗控件，否则它们混进渲染与控件清单）、`run:true`、`settleSec:0.5`。
`saveAs` 可把结果存进模拟器工作区；`mountTo` 指定挂在哪个控件上（默认服务端容器节点）。

**★ 配方 `last-bind.json`（重启后一键重搭）**：`op=bind` 成功时会把它用的**源文件 + 交接值**记一小份配方到模拟器工作区。
为什么必须有它 —— **Host 是启动时的快照**：每次重启 `dsh web`，模拟器内存里的工程都回到出厂默认
（`op=state` 的 `factoryDefault:true`；用户 2026-09-24 实测那次"试玩页里只剩默认的文本/按钮/五角星"就是它）。
重启后 `{"op":"bind","last":true}` 一键重搭，面板上也有对应按钮（**不自动重搭** —— 那会擅自在人没要求时改工程）。

**真机实测（双相，2026-09-24，370ms 建好）**：

```
run.logs:  [yuan-code] OnInit / OnEnable / OnStart -> STARTING 挂载核对（容器交接值=1073741866）
           [yuan-code] 关卡1 可达性审计: 通过（平台 15，逐段均在预算内；移动平台按最优相位估算）
           [yuan-code] RUNNING -> 《冰镜·火烛》就绪（3 关，控件 31，画布 1600x900）
run.controlCount = 32（= 容器 1 + 双相 31）   frame=17  time=0.57
```

⚠️ 它**不做**的事：不猜模板索引、不猜控件类型、不猜容器索引（缺哪个就报错）。编造交接值的代价是"看起来跑起来了"。

## 4.13 验收单（`op=cases`）★ 2026-09-24 补

**它解决什么问题**：`verify` 是一次性的（跑完就没了），而"这一版该怎么验收"是**要沉淀下来**的：
下次改完，人还是照上次那套点，AI 还是照上次那套断言 —— 否则每次都在重新定义"算不算过"。

清单存在**模拟器工作区的 `cases.json`**（`<dataRoot>/simulator/cases.json`，不碰游戏存档），人和 AI 读**同一份**：

| action | 做什么 |
|---|---|
| `list`（默认） | 每组一行：`autoCount` / `manualCount` / 每条用例的 `kind`（auto / manual）+ 事件数 + 断言数（**不给全量 events，省 token**） |
| `show` | 某一组的用例全文（要抄/要改的时候用） |
| `add` | `set=<名字>` + `cases:[{name,steps,expect}]`；**同名 = 覆盖**（改断言再存一遍）。加 `fromHistory:true` 就把**刚跑过那一局**的操作变成用例（AI 不用手抄 events）。`{manual:true, note:"…"}` = 人工项 |
| `run` | 自动项走 `verify` 的确定性重放；**人工项不代跑**，只列进 `manual[]` 等人打勾。可按 `cases:[名字]` 只跑其中几条 |
| `remove` | 默认 **dryRun**（只说会删什么）；真删要 `confirm:true` |

**两条纪律写进回执里**：

1. **`autoPassed` ≠ 验收通过** —— 返回里直接写「自动项已跑完（2/2）—— 但**整组没算过**：还有 N 条人工项要人确认」。
2. **人工项不写 `note` 就报错** —— note 是"人要看什么、看到什么算过"，没有它这条单子等于没写。

`op=verify caseSet=<名字>` 也能直接跑清单里那一组（人/AI 同一份入口）。

## 5. 三条安全纪律（改动时别绕）

1. **用户 Lua 一律跑在可终止的 Worker 里**（引擎自带的 `worker_threads.Worker`，默认单次操作 8 秒超时后 `terminate`）。
   实测：塞一段 `while true do end`，`play start` 在超时后**返回错误**而不是挂住，随后 `stop` 仍可用（`tests/sim-test.mjs` 有断言钉住）。
   意义：控制台/Web GUI **不会**被一条失控脚本冻死。
2. **工作区固定在本插件数据目录下的 `simulator/`**（`<dataRoot>/simulator`）—— 模拟器的存档读写只发生在这里，**永不指向游戏存档、地图或活文件目录**。
3. **插件卸载/重挂时 `disposeSimAll()`** 收掉所有会话的 Worker，不留幽灵进程。

## 7. 排障

| 症状 | 处理 |
|---|---|
| 面板/工具里没有 `miliastra_sim` | **Host 是启动时的快照** —— 改了 `index.js` 要**重启 `dsh web`** 才生效（面板顶部的版本行会显示 `Host vX / 源码 vY` 与陈旧警告） |
| 三个 tab 不出现 | ① 先**刷新页面**（只有 `lib/client.js` 变了）；② 还看不到就用**侧边栏浮层顶部那条三等分页面条**（初级/高级/模拟器）；③ 想确认注册成功没有：用 `cordis_inspect_query` 读客户端 `Slots` 的 `conversation.view` **occupants**（2026-09-24 实测能看到三条 `active: true`）—— **别靠猜** |
| `@napi-rs/canvas` 装不上 | 支持本机五个平台包之外的平台时，`op=shot` 会失败；引擎其余部分（`state`/`patch`/`play`）不需要它 |
| `play worker timed out` | 脚本里有慢/死循环（这就是护栏在工作）：先看日志，再看是不是 `while true`。可用环境变量 `QXQY_PLAY_TIMEOUT_MS` 调整（默认 8000） |
| **试玩页/iframe 一片黑、Frame 停在 0** | ① 先看页面上有没有**红条报错**（2026-09-24 起报错条常驻在 header 下面 —— 以前它藏在默认折叠的侧栏里，所以只剩"黑"）；② 如果点了「开始试玩」却**一点反应都没有**（连报错都没有），那多半是**路由把 `op` 吃掉了**：`/miliastra/engine` 曾经写成"有 `body.args` 就用 `body.args`"，而 `op=play` 的参数本来就装在 `args` 里 ⇒ 每次调用退化成 `op=state` 且不报错。自证一条：`curl -s -X POST -H "content-type: application/json" --data-binary '{"op":"play","action":"history"}' http://127.0.0.1:3080/miliastra/engine` —— 回 `{"action":"history",...}` 才对，回一个 **state 快照**（有 `treeCount`、没有 `action`）就是旧版 Host |
| 面板「模拟器」页右侧空白 / 试玩页被滚走 | 2026-09-24 起改成**左列自己滚、右列不动**；如果还看到旧行为，是浏览器里的旧 bundle（**F5**）或旧 Host（**重启 `dsh web`**） |
| **重启 `dsh web` 后试玩页里只剩「文本 / 预设按钮 / 五角星」** | 不是渲染坏了：**Host 重启后内存里的工程就是出厂默认**。`op=state` 会报 `factoryDefault:true`；面板顶部有提示 + **一键重搭上次**（配方 `simulator/last-bind.json`，成功 bind 时自动记）。没有配方就先展开「④ 工程与控件树 / 工程适配」重新扫描活文件搭一次 |
| 左列按钮/文字**叠在一起** | 左列是固定高度的 flex 列，子项默认会被压扁（`flex-shrink:1` + `min-height:0`）。2026-09-24 起子项一律 `flex:0 0 auto` —— 还看到旧行为就是旧 bundle（**F5**） |
| **试玩页的画布是一个小方块、四周全是空**（作者实测「右侧这么大的画面也太小了吧」） | `fit()` 在页面刚插进 iframe 时量到的是**还没定尺寸的盒子**（~330×180），一写下去就再也没重算。2026-09-24 起：盒子 <200×150 先不写、下一帧再量；**每帧快照节流重算**（0.35 秒追平）。判据看 footer 上的 **`画布 W×H（可放 W×H）`** —— 两者差太远就是没追平。⚠️ `play.html` 是**每次请求现读**的（`Cache-Control: no-store`），所以改它**不用重启 Host**，点面板「重载页面」或 F5 即可 |
